# Обзор технологии

`shuttle-replay` превращает в повтор три вида данных: локальное исходное
видео, 2D-детекции волана, которые предоставляете вы, и ограничения, которые
проверил человек (точки калибровки, касания и зоны приземления). Эта страница
служит картой. Пять следующих за ней страниц подробно объясняют каждый этап, и
каждая страница ссылается на точные строки исходного кода, которые она
описывает, закреплённые на коммите
`6e9a060b5cc964f02d4017d806e953ffea89c8b4`.

## Поток данных

```text
 source video (local file) ----------------------------------------+
                                                                   |
 calibration input JSON --> calibrate --> calibration JSON         |
 (ground points + net anchors)              (P, H, errors)         |
                                                 |                 |
 tracks JSON (your detections, PTS) -------------+                 |
 review JSON (contacts, flight ends) ------------+                 |
                                                 v                 v
                                       analyze --> analysis JSON --> render --> replay MP4
                                                                         +--> render report JSON
```

CLI предоставляет каждую стрелку как команду: `calibrate`, `analyze`, `render`
и `run` (analyze + render за один шаг). `demo` строит полностью синтетическую
сцену и прогоняет на ней тот же конвейер
([`cli.py` `build_parser`](https://github.com/KAIROS03/shuttle-replay/blob/6e9a060b5cc964f02d4017d806e953ffea89c8b4/src/shuttle_replay/cli.py#L154-L191)).
В `run` видео рендерится и проверяется до записи `analysis.json` и
`render_report.json`, поэтому JSON-результаты никогда не описывают видео,
которое не удалось создать
([`_run_pipeline`](https://github.com/KAIROS03/shuttle-replay/blob/6e9a060b5cc964f02d4017d806e953ffea89c8b4/src/shuttle_replay/cli.py#L55-L63)).

Что добавляет каждый этап:

1. **Калибровка** превращает проверенные пиксельные позиции известных точек
   корта в гомографию пола `H` и матрицу камеры 3x4 `P` для каждого сегмента
   камеры. См. [Калибровка камеры](camera-calibration.md).
2. **Проверка входных данных** проверяет временные метки, сегменты, касания и
   концы полётов и отклоняет несогласованности вместо того, чтобы их
   исправлять. См. [Наблюдения и время](observations-timing.md).
3. **Подгонка полёта** подгоняет модель с гравитацией и квадратичным
   сопротивлением к 2D-детекциям между проверенными касаниями. См.
   [Физика траектории](trajectory-physics.md).
4. **Рендеринг** декодирует исходник, рисует наложения и вид корта сверху,
   копирует аудиопакеты и проверяет результат перед публикацией. См.
   [Рендеринг и безопасность вывода](rendering-safety.md).
5. **Валидация** распределена по всем этапам. Что доказывает каждая проверка и
   чего она не доказывает, собрано в
   [Валидация и ограничения](validation-limits.md).

## Программный стек

| Компонент | Роль в этом проекте |
| --- | --- |
| Python 3.12+ | Язык; `requires-python = ">=3.12"` в `pyproject.toml` |
| NumPy | Линейная алгебра: DLT для гомографии, SVD, проекция, решение для якорей методом наименьших квадратов |
| SciPy | `solve_ivp` интегрирует ОДУ полёта; `least_squares` подгоняет полёты |
| PyAV (`av`) | Привязки FFmpeg внутри процесса: декодирование, кодирование, копирование аудиопотока, проверка |
| Pillow | Рисует кольца, следы, корт и текст на каждом кадре |
| uv | Устанавливает зафиксированное окружение (`uv.lock`) и запускает команды |
| Sphinx + MyST + Furo | Собирает этот сайт документации (группа зависимостей `docs`) |

Зависимости времени выполнения: ровно `numpy`, `scipy`, `av` и `pillow`
([`pyproject.toml`](https://github.com/KAIROS03/shuttle-replay/blob/6e9a060b5cc964f02d4017d806e953ffea89c8b4/pyproject.toml#L10-L15)).
Ни один подпроцесс или команда оболочки не строится из имён файлов; работа с
видео идёт через PyAV в том же процессе Python
([docstring модуля `render.py`](https://github.com/KAIROS03/shuttle-replay/blob/6e9a060b5cc964f02d4017d806e953ffea89c8b4/src/shuttle_replay/render.py#L1-L7)).

## Почему нет встроенной модели

Найти волан в кадре (детекция) и определить, где он находится в 3D
(реконструкция), это разные задачи. Этот проект решает только вторую, и только
при явных допущениях. Нет ни детектора, ни нейронной сети, ни весов модели для
загрузки. Вы приносите детекции из любого инструмента, которому доверяете, в
формате `shuttle-replay/tracks/v1`, описанном в [схемах](schemas.md).

Так каждое число остаётся отслеживаемым. Каждый кадр анализа помечает позицию
волана слоем происхождения
([`PROVENANCE`](https://github.com/KAIROS03/shuttle-replay/blob/6e9a060b5cc964f02d4017d806e953ffea89c8b4/src/shuttle_replay/analysis.py#L33-L38)):

- `observed_pixel`: ваша детекция без изменений или null, если её не было.
- `human_review`: касание, зона приземления или точка калибровки, введённые
  человеком.
- `conditional_model`: подогнанная физическая модель, которая хороша ровно
  настолько, насколько хороши калибровка и проверка, которыми она обусловлена.
- `display_interpolation`: линии, которые рендерер рисует между отсчётами
  модели.

Пропущенная детекция никогда не заполняется так, будто она наблюдалась, и
модель никогда не помечается как измерение.

   защищается MP4.
